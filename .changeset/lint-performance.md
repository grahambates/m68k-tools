Make linting a large file faster. Measuring the impact of each suggestion split the whole source into lines every time, so the cost of a lint grew with the number of suggestions times the length of the file, and a 40,000-line file took three times as long as a 20,000-line one; it now splits once and grows in proportion to the file (a 20,000-line file with about 8,000 suggestions goes from 4.6 s to 2.3 s). The language server also keeps the diagnostics it computed for each version of a document, so a code-action request, which arrives whenever the cursor moves, no longer lints the same text again; edits, saves, configuration changes and file changes discard them. "Fix all" is no longer built on every code-action request, where it ran the whole lint-and-apply loop (ten full lints, 17 seconds on a 20,000-line file with many fixes) even though the client was only asking for quick fixes as the cursor moved. A client that can resolve a code action's edit is now offered it without one, titled without a count, and the edit is built when it is chosen; a request for other kinds of action does not include it; a request for `source.fixAll` (as on save) still builds it straight away, as does a client that cannot resolve edits. It is only offered when it would change something. Indexing a large project is much faster and no longer stops the server. Following the includes of a project with thousands of files looked every include up in every main source's directory, once per file that names it; it now looks each name up once, and rules out most directories from a listing read once instead of a system call each, which took the index of a 3,000-file, 240,000-line project from 12.6 s to 5.6 s. Saving a file used to throw the index away, so the diagnostics that followed waited for the rebuild (14 s, then 5.5 s); the old index is now kept, the diagnostics come back at once (about 0.1 s), and the open files are linted again when the new index is ready. The rebuild starts two seconds after the last save, so saves that keep arriving (such as an auto-save after every pause in typing) are one rebuild and not one each; one that is already running is left to finish, followed by one more if there were saves meanwhile, and the open files are linted again once, when it has caught up. The index is built in small steps that let the server answer other requests, where before a request could wait over three seconds behind it. `buildProjectSymbolsAsync` and `buildProjectReferencesAsync` are new in `m68k-lint`, and give what the existing functions give.
